## 二、阶段目标与所有权

```text
用户/API → Dataset/Job 元数据（Go + MySQL）
             │        Job ID、状态、幂等键
             ▼
       存储适配（MinIO/S3）
             │        不可变输入快照、attempt 对象、已发布清单
             ▼
       本地 scratch + 现有 Python 算法
```

- MySQL 管身份、状态、关联和幂等；MinIO 管大文件与清单；本地 scratch 只是一次执行的工作目录。
- Go 只做轻量控制面和提交校验，不在 API 请求内同步跑重建算法或读取整张图进数据库。
- 本阶段暂用一个本地执行器/命令把 Job 走通，不提前接入 Argo/Ray。状态 API 必须表达 `pending/running/succeeded/failed/cancel_requested` 等合法迁移；具体名称可依据现有代码调整。

## 三、代码实现

1. 增加 MinIO/S3 兼容存储适配：固定版本本地 Compose 或等效开发环境、配置示例、上传/下载、SHA-256/大小校验、带前缀隔离的对象键。禁止凭据硬编码；`.env`、数据卷和缓存应被忽略。
2. 基于 Phase 1 合同，上传合成输入快照，生成只含对象 URI 的清单。算法执行时下载到 job 独立 scratch，并调用原有 `store_vision` 链路；产物先上传 `attempt/<id>/`，全量校验后写最终 manifest/发布指针。若使用对象复制或条件写，说明其原子性范围。
3. 建立最小 Go API 与 MySQL migration：Dataset 注册、Job 提交/查询、Artifact 查询、取消请求。数据表至少能追踪 dataset/run/stage/artifact、状态版本、尝试次数、失败类型、输入/输出 manifest URI 和幂等键。API 输入须校验长度、枚举、身份与资源归属。
4. 提交请求通过唯一约束实现幂等；同键同请求返回同 Job，不同请求体返回冲突。并发状态更新使用条件更新/版本检查，不由最后一个写入者随意覆盖结果。
5. 实现最小执行器或过渡协调器，避免 API 进程阻塞。说明本阶段它和 Phase 4 Argo 的替换关系。若取消尚不能中断算法，API 必须诚实标示 `cancel_requested`，不可声称已经取消。

## 四、失败与一致性实验

自动化测试覆盖：重复提交、并发提交、坏 checksum、部分上传、对象不存在、MinIO 暂时不可用、API/执行器重启后状态读取。至少实际运行一次合成样例从注册到结果查询，并记录对象键与状态序列。

明确讲清两件事：对象存储上传和 MySQL 提交之间**没有跨系统事务**；“上传成功但数据库更新失败”会留下不可见 attempt，可由重试复用或清理。不能因为 HTTP 200 就认为计算完成，提交返回的是 Job 身份和当前状态。

## 六、代码完成后的教学式讲解

选下面四条中的至少三条，使用实际文件/函数/表字段，不只讲概念：

1. **提交 Job**：HTTP → 参数校验 → 幂等唯一键 → MySQL Job → 返回 ID；解释为什么长计算不在请求线程中。
2. **大文件流转**：输入快照 → MinIO → scratch → 算法 → attempt 对象 → manifest；解释数据库只存什么。
3. **部分失败**：上传后、DB 更新前崩溃时，对外能看到什么、怎样重试/清理、为什么不能称“恰好一次”。
4. **取消请求**：谁记录意图、谁检查、何时真正停止、已经发布的产物是否仍可见。

每条说明职责、调用关系、设计取舍、合同字段、失败与重试语义及分布式边界，给用户一个可执行小实验、预期状态和日志/对象观察点。
