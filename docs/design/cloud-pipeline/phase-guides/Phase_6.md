# Store Vision Cloud Phase 6：部署、性能验收与项目讲述

你现在在 `PRINCEofAsgd/3D-Recons` 最新 `main` 上完成[总体计划](../phases.md)中的 Phase 6。你负责把已有 Demo 做成另一环境可复现的交付，完成真实性能实验、文档和最终教学总结。先核对 Phase 1～5 的代码与故障证据；不要把尚未实现的设计写成“已完成”。

## 一、项目规则和环境基线

第一步读取根目录 `AGENTS.md` 并严格遵守文档职责、中文注释、上下文 Step、版号、数据与凭据边界。检查已有变更，阅读结构、开发、上下文与实际部署文件。测试只用合成/去标识化样例，不上传真实数据。开发命令应能在干净环境中执行，不能依赖作者机器的绝对路径。

## 二、最小可复现部署

1. 固定镜像版本和构建输入，提供 API、算法/阶段容器、Ray、Argo 及 MinIO/MySQL Demo 依赖的本地 Kubernetes 配置；避免未固定 `latest`。资源 requests/limits、健康检查、工作目录、scratch 容量与超时要与任务特点匹配。
2. 配置示例只放占位值；本地密钥通过 Secret/环境注入，真实密钥与数据卷不得提交。明确 Demo 单点组件与生产高可用的区别；不因为运行在 K8s 上就声称存储或数据库已高可用。
3. 在新建环境按开发文档从构建、迁移、部署到提交合成样例，最终查询 Job、下载/查看 2.5D GeoJSON 或拼接图、核对对象 manifest。重启一个 worker 后再次运行，确认状态和结果仍可追踪。
4. 输出一份简洁的资源与数据流图，标明控制面、数据面、编排面、计算面和原算法代码各自在哪个容器/服务中。

## 三、性能实验方法

1. 固定合成数据集、图片数/尺寸、画布配置、算法参数、候选、镜像、节点 CPU/内存、预热与重复次数。测量端到端总耗时、API 接受时间、共享标定、Ray map、全局 reduce、对象上传下载、2.5D 分支的分段耗时和资源峰值。
2. 对照**串行、Ray 1 worker、Ray 2 worker、可用时 Ray N worker**；至少重复数次，报告中位数/波动范围与扩展效率。不能把多个 worker 进程伪称为多个物理节点。
3. 核对每组输出尺寸、GeoJSON 要素/拼接统计和校验和或约定数值容差。若为了速度更改输出质量，必须单独标示，不能作为等价性能对照。
4. 分析非线性扩展：全局标定、对象传输、Ray 调度、内存/CPU、全局 reduce；区分“加速逐相机计算”和“加速整个 Job”。只给实测数据，不虚构 TB/PB、高并发或生产 SLA。

## 四、收尾验收

- 冷启动：全新本地环境可按文档完成合成样例。
- 合同：云端 URI、版本、哈希、候选、坐标/单位和 lineage 可核对；旧本地 CLI/GUI 回归通过。
- 调度：Argo 阶段依赖与 Ray 逐相机并行均有真实运行证据。
- 故障：Phase 5 的关键恢复场景仍通过；发布产物不被旧 attempt 覆盖。
- 资源：对象存储、数据库、Pod 和 scratch 的容量/清理策略有说明。
- 诚实边界：列出已实现、仅设计、未验证和生产化仍需工作；不把该 Demo 说成原实习生产系统。

按 `AGENTS.md` 更新结构、开发、必要操作文档、上下文 Step、版本位置和 `.gitignore`。最终架构与验收结果放在适合的正式文档，不把学习笔记或对话实录放进 `docs/record`；仅用户明确要求时归档阶段摘要。

## 五、代码完成后的教学式讲解

从真实代码和运行日志中挑四条最高价值链路，按“入口 → 调用 → 资源/状态 → 输出 → 故障”讲：

1. **一次完整 Job**：API/DB → Argo → 中间层 → 两个分支 → artifact；每层职责与数据合同。
2. **Argo 与 Ray 调度边界**：DAG 节点和逐相机 task 的粒度、资源调度和重试归属。
3. **可靠发布**：attempt、校验、状态版本、manifest 指针、对账；为何重复执行仍可只有一次可见结果。
4. **扩展瓶颈**：用本阶段分段计时解释 worker 增加后哪部分可加速、哪部分不能及下一步优化选择。

每条给用户一个能亲手执行的观察/故障/性能实验，包含预期现象、自我检查问题与实际证据文件或界面；讲清控制面、数据面、编排面、计算面的分布式边界。最后给一段**可用于面试但严格属实**的项目表述，清楚说这是在原算法项目基础上独立扩展的云端分布式 Demo，列出真实验证规模与限制；不要声称原岗位曾上线此系统。
