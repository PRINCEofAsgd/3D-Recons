## 二、只拆真实独立计算

现有 `run_parameter_stitching` 在一个循环内逐相机去畸变、投影、生成有效 mask/权重，随后维护全局 accumulator、overlap 和输出。请做有界重构：

1. 将**确定共同画布**保留在驱动端，画布配置、候选、坐标系、单位、算法版本形成所有相机共享的只读输入。
2. 提取可复用的纯逐相机函数，输入为一个相机的图像引用/参数和画布快照，输出为该相机的 warped 像素、有效 mask、权重/诊断元数据；确保原串行实现也调用它，避免分叉维护两套算法。
3. 用 Ray task 按相机并行执行；任务只读取本相机资源和不可变中间层，不写同一全局数组。大图不通过驱动进程重复广播；必要时从对象存储按需读取并把分片存回 attempt 前缀。
4. 驱动端等待所有**必需**分片成功，再按稳定相机顺序执行全局 reduce：覆盖统计、权重融合、裁剪、输出 manifest。某个分片失败时不得读取半成品，也不得发布成功结果。
5. Ray 任务参数显式声明 CPU/可选 GPU/内存需求与最大在途数，防止相机数增加导致驱动端内存无界。保留可在无 Ray 环境运行的串行路径。

共享 K/D 联合标定与跨相机去重是全局依赖，**不能**为了“展示分布式”拆成互不相干的相机任务。2.5D 本阶段维持现有消费者；只在有清晰独立输入/汇总合同时增加逐相机检测并行。

## 三、分片合同与重试

每个分片以 `(job_id, run_id, candidate, canvas_hash, camera_id, task_version)` 为业务身份，以 `attempt_id` 区分执行。分片 manifest 记录输入图 SHA-256、标定/画布摘要、结果 URI/校验和、尺寸和相机 ID。一次 task 失败可重试，但每次写到独立 attempt；reduce 只挑通过校验的目标 attempt。发布前检查相机集合完整且无重复。错误 schema/候选/画布属于不可重试合同错误；临时对象读取/worker 故障属于有界重试。

## 四、验证要求

1. 使用同一合成样例比较原串行和 Ray 输出尺寸、覆盖数、相机统计、最终像素差异；预先写明容差并解释有无浮点顺序差异。
2. 在至少两个 Ray worker **进程或节点**上执行，记录 task ID、相机 ID、worker 标识和耗时，证明不是一个进程里的普通循环。
3. 注入单相机失败或杀死一个 worker，观察只重试受影响分片、全局结果未提前发布；重复执行同一 task 不覆盖已发布产物。
4. 运行项目关键回归测试。若环境不支持多节点，可用本机多进程验证，并如实标注物理节点未验证。

## 五、正式文档与教学式讲解

按 `AGENTS.md` 更新结构与开发说明、上下文 Step、版号位置和必要的用户说明。写明 Ray 本地启动/停止与资源配置、串行回退命令、合成样例验证命令。运行日志和数据不得提交。不要提前接入 Argo。

代码完成后，用**一张 map/reduce 调用图**和具体函数讲三条链路：

1. 标定候选/共同画布 → 逐相机 Ray task → 分片合同：为什么画布必须先定，任务为何可并行。
2. 全部分片 barrier → reduce → 拼接 manifest：为什么覆盖/融合不能由多个 worker 直接并发改同一数组。
3. worker 崩溃 → attempt 重跑 → 校验 → 单次可见发布：谁决定重试，什么时候结果对外可见。

每条讲职责、调用顺序、数据合同、分布式边界和失败语义，并给用户一个可亲手执行的实验及预期现象。区分 Ray worker 与 Kubernetes Pod 的概念。最终答复列出文件、实测结果、测试、性能数字的测试条件、未验证边界、讲解和建议提交说明。现在从只读检查开始。
