# Store Vision Cloud Phase 5：失败、重试、恢复与可观测性

你现在在 `PRINCEofAsgd/3D-Recons` 最新 `main` 上完成[总体计划](../phases.md)中的 Phase 5。你负责完成故障处理代码、真实故障实验、测试和正式文档；最后把失败语义用项目实际链路教给用户。先核对 Phase 1～4 的实际实现与测试，不凭计划文档假设功能存在。

## 一、规则和准备

第一步读仓库根 `AGENTS.md` 并严格遵守；按需读 README、结构、开发、上下文与源代码。保护已有变更。使用合成/去标识化测试数据，禁止提交凭据、真实输入、对象存储数据卷与日志。每次代码修改按规则写必要中文注释、同步正式文档、在项目上下文顶部维护 Step、同步版号和 `.gitignore`。

## 二、写清楚状态机和错误分类

1. 从现有 Job/Stage/Task 表、Argo 节点、Ray task 与对象产物梳理事实来源。给出状态转移表：谁可以从 `pending` 领到 `running`，谁能终结，取消与超时如何处理，并发更新如何拒绝旧 attempt。
2. 错误至少分三类：合同/输入不合法（不可自动重试）；对象存储/网络/Worker 暂时故障（有界退避重试）；算法质量门禁不通过（需调整输入或参数，不能盲目重试）。每类在 API 状态与日志中可辨认。
3. 确定重试预算属于哪一层。Argo 阶段重试和 Ray 分片重试不能相乘成无界执行；明确最大次数、超时、退避和超预算后的终态。

## 三、实现可见性与恢复

1. 每次执行写入独立 `attempt_id` 前缀。先上传结果和完整性校验，再以条件写/数据库状态版本更新发布指针；读者只使用成功发布的 manifest。S3/MinIO 与 MySQL 无跨系统事务，不要称为严格的 exactly-once 执行。
2. 实现重启后的 reconciliation：扫描/查询非终态 Job 和 orphan attempt，对照对象校验与数据库版本，选择重试、完成发布或保留待人工处理。回收有界且只删本 Demo 明确拥有、超出保留期的未发布 attempt；不得碰原始输入和已发布产物。
3. 支持取消请求与超时。停止新 task、尽力中断在途任务、记录实际停止/未停止结果。已经完成且发布的产物不能被取消逻辑悄悄覆盖。
4. 防止同一 task 的旧 attempt 在新 attempt 成功后回写最终状态；用唯一约束、版本/CAS 和发布身份校验。记录为什么“至少一次执行，至多一次对外可见发布”只在这些条件下成立。

## 四、可观测性

API、Argo 阶段命令、Ray task、存储适配和最终产物都携带 `job_id/run_id/stage_id/task_id/attempt_id`（按实际阶段适用）。结构化日志避免个人信息与绝对路径；指标至少含阶段/分片耗时、成功失败数、重试次数、在途数、输入输出字节、对象存储错误和等待时间。给出一条从 API 到具体失败分片的排障路径。可用 Prometheus，但不要为了 Dashboard 引入与 Demo 规模不符的依赖。

## 五、必须真正验证的故障矩阵

| 故障点 | 应观察的结果 |
| --- | --- |
| 合同 schema/校验和错误 | 快速失败，不进入无意义重试 |
| Worker 执行中退出 | 受影响 task 有界重试，旧 attempt 不发布 |
| 结果已上传、DB 更新前退出 | 对外不可见半成品，重启后可对账 |
| 发布回报重复/乱序 | 状态不回退，不出现两个可见版本 |
| MinIO 暂时不可用 | 退避重试或明确失败，避免无限阻塞 |
| 取消/超时 | 不再领取新任务，状态与已发布结果一致 |

为每个场景写自动化测试或可复现注入命令，实际执行至少关键四项；未执行项明确标待验证。记录测试输入、故障触发点、Job/Stage/Task 状态、对象前缀、日志关联 ID 和恢复耗时，不伪造结果。

## 六、代码完成后的教学式讲解

请挑四条链路：**普通成功、Worker 崩溃、上传后状态前崩溃、重复回报/取消**。逐条使用时间线说明：哪个组件持有哪些状态，谁检测失败，谁决定重试，何时检查合同，何时结果对外可见，数据库、对象存储与计算 Worker 的分布式边界在哪里，以及为什么不存在数据库与对象存储的原子事务。让用户亲手运行至少两个故障实验，并给预期的状态/日志/对象观察点及自我检查问题。
